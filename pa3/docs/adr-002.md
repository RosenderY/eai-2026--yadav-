# ADR-002 — Correlation, idle timeout, partial results, and duplicate handling

**Status:** accepted  
**Date:** 2026-10-05

## Context

The router splits one order into several independent item messages, and those
items can travel through different queues and workers and return in a different
order. The aggregator therefore needs enough information on every message to
know which order it belongs to, how many items are expected, and which item a
result represents.

The aggregator also cannot wait forever if one worker never responds. At the
same time, normal processing can take different amounts of time, especially for
larger orders. Duplicate deliveries are also possible, so counting every
message as a new result would be unsafe.

## Decision

The router copies the original order identifier into both `orderId` and
`correlationId` on every split message. It also adds `itemIndex` and
`totalItems`. The aggregator groups state by `orderId` and stores results
inside that order by `itemIndex`.

I use an idle timeout of 5 seconds. The order's `last_activity` timestamp is
updated whenever a valid item result arrives. A background sweep checks once per
second and publishes a partial result when an incomplete order has been idle for
at least 5 seconds.

A partial result contains the results that did arrive, the number received, and
`missingItemIndexes` listing exactly which item indexes never produced a
result. A complete result also contains `missingItemIndexes`, but as an empty
list.

Duplicates are handled by storing results as
`results[itemIndex] = result`. If the same item is delivered again, it
overwrites the same entry instead of increasing the result count. Completed
order IDs are also remembered so a late duplicate does not create a second
completion message.

## Alternatives considered

I considered using a fixed deadline measured from when the first result for an
order arrived. I rejected that because a larger order can still be making
healthy progress when the deadline expires. Resetting an idle timeout after
each result better represents the actual failure case: no new result has
arrived for some time.

I also considered storing aggregation state in a persistent database such as
Redis instead of memory. That would survive an aggregator restart, but it adds
extra infrastructure and I/O that are unnecessary for this assignment.

Another alternative was to append every received result to a list and check the
list length. I rejected that because a RabbitMQ redelivery could make the same
item count twice and cause an incorrect completion.

## Consequences

The design keeps concurrent orders separate and makes out-of-order delivery and
duplicates straightforward to handle. It also guarantees that a missing worker
produces an honest partial result instead of an order that hangs forever.

The main cost is that aggregation state is only in memory. If the aggregator
container restarts while an order is incomplete, that in-flight state is lost.
The `completed_orders` set is also in memory, so it does not provide permanent
deduplication across restarts. For a production system with longer-running or
business-critical orders, I would move this state to a durable store.
