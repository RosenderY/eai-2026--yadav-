# ADR-003 — Source adapters around one canonical order

**Status:** accepted  
**Date:** 2026-10-13

## Context

PA4 receives one business concept through three incompatible source contracts. The web source is nested JSON, the mobile source uses abbreviated fields, a Unix timestamp, numeric codes and a single address string, while the B2B source is XML with a Windows-1257 declaration and XML attributes. The product identifiers also arrive in three different forms even though they refer to the same catalogue products.

Prices cannot be trusted from the source messages. They must come from the pricing service, which can answer successfully, return 404 for an unknown product, return another HTTP error, or be unreachable. Every source also carries payment information that is intentionally absent from the canonical schema.

## Decision

I keep translation at the edges and share only the work that is genuinely common. Each source translator first produces the canonical business fields and normalized item identifiers. A shared `assemble` step enriches the normalized lines from the pricing API and adds `receivedAt`.

Product IDs are normalized before lookup: web IDs pass through, mobile IDs receive the `PROD-` prefix, and B2B IDs lose the `SKU-` prefix. Monetary values from the pricing API are formatted with `toFixed(2)`, making values such as `4.5` become the required decimal string `"4.50"`.

Pricing failures do not throw out of the translator. A 404 becomes an `UNKNOWN_PRODUCT` warning; other HTTP or network failures become `PRICING_API_ERROR`. The failed item is left out and healthy items continue. If every item fails, the result contains `order: null` because the canonical schema requires at least one item.

Payment data is filtered by construction rather than deletion. The canonical order is built field by field, so web payment objects, mobile PAN/expiry fields, and B2B payment/IBAN data are never copied into the result.

## Alternatives considered

One alternative was to copy each source object and then delete unwanted fields. I rejected that because it is a denylist: a new sensitive field could travel forward automatically. Explicit canonical construction is an allowlist and is safer.

I also considered failing the whole order if one product could not be enriched. That would make the code simpler, but it would discard valid line items and contradict the assignment's warning-based partial-result behavior.

A pricing cache was another option. It would reduce repeated HTTP requests, but it would introduce staleness and would make live price changes harder to observe. For PA4, direct lookup is clearer and matches the requirement that the pricing service is authoritative.

## Consequences

The three input formats now converge on one canonical representation while preserving source-specific parsing logic at the boundary. Unknown B2B elements are naturally ignored because the translator reads only the fields it understands, which supports the tolerant-reader requirement.

The trade-off is that every item causes a pricing call, so translation latency depends on the pricing service. The mapping code also has to change if the canonical schema gains a new required field. If another source is introduced later, it needs its own adapter and product-ID normalization rule, but the enrichment and canonical assembly logic can remain shared.
