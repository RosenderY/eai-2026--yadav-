# ADR-004 — Durable retry routing and notification deduplication

**Status:** accepted
**Date:** 2026-10-26

## Context

Orders fan out to payment, inventory, and notification consumers. Network failures cause duplicates, malformed messages are permanent, and a consumer can fail without any other service failing. RabbitMQ's course topology retries through a TTL queue and direct return exchange.

## Decision

The order service generates UUIDv4 `correlationId` in the AMQP custom `headers`, not in the canonical JSON body or native `properties.correlationId`, because the schema disallows extra body fields and the assignment's consumers examine `headers.correlationId`. Every result event forwards this header.

Each consumer declares the same durable dead-letter and invalid-message fanout exchanges, queues, and bindings before consuming. Invalid JSON, absent correlation identifiers, and missing order identity are permanent and go immediately to `orders.invalid`, preserving original bytes and headers. Simulated service errors are transient: dead-letter to a 1-second TTL retry queue, then return to only the originating consumer; after the third failure publish to `orders.dlq` with the `originQueue` header.

Notifications deduplicate on the correlation ID, loaded and saved in the bind-mounted file `/data/processed-ids.json`. A duplicate is acknowledged and does not append to `notification.log`. DLQ replay strips `x-death` through `withoutRetryHistory` and routes via `orders.return.exchange` using `originQueue`, resetting the attempt budget.

## Alternatives considered

An in-memory Set would lose processed identifiers on restart. Immediate requeue bypasses the delay and risks an infinite hot loop. Republishing retries to the original fanout would duplicate work in unaffected services. A single error queue would mix permanent format defects and exhausted transient failures. Three attempts and a 1-second TTL follow the supplied course topology; production settings should account for service recovery time.

## Consequences

The correlation header supports tracing, and durable queues preserve failures for inspection and selective replay. Replay while a provider is still down will return messages to the DLQ. A file works for one notification consumer but does not provide a multi-replica atomic uniqueness guarantee; a crash between appending the notification and recording the ID may still duplicate work. Production needs a transactional idempotency table, publisher confirmations, DLQ alerts, and compensation for successful payments when inventory ultimately fails. PA5 does not implement that saga.
