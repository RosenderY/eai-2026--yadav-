# ADR-005 — A single coordinator for checkout fulfilment

**Status:** Accepted  
**Date:** 2026-11-02

## Context

The canonical order enters checkout without payment credentials or a pre-calculated total. Four independently running services must participate in fulfilment, and they cannot share one database transaction. Payment must be approved before stock is reserved; shipping and the customer message must wait until both earlier operations have succeeded. A failure after a remote service has acted leaves a partial business result, not a transaction that can simply be rolled back.

The coordinator also needs to tolerate client retries. A network timeout is ambiguous: a service may have completed its work even though the caller did not receive the response. The implementation therefore needs an explicit request identity, a durable record of completed outcomes, and a trace of the calls it actually observed.

## Decision

The API contract is maintained in `openapi.yaml` and linted by the local Spectral ruleset before implementation. `POST /checkout` receives the canonical order without adding fields to it and requires an `Idempotency-Key`. The contract documents validation, key conflicts, downstream failures and timeouts. It limits the `items` collection to 50 entries; the coordinator enforces the same limit.

A single TypeScript process owns the workflow. It calls payment authorization, inventory reservation, shipping creation and notification in that strict order. The payment total is calculated from the decimal-string unit prices using integer cents, then sent to the payment mock as a two-decimal string. The notification destination is taken from `customer.email`. Each HTTP call has a configurable deadline and produces a trace record containing its operation name, outcome, start and finish timestamps, and elapsed milliseconds.

If a forward operation fails, the coordinator visits completed operations in reverse order. It releases reserved inventory and refunds an authorized payment. Shipping creation and notification have no reverse endpoints in the supplied mock services, so the coordinator does not pretend that these external effects can be erased. A failed compensation changes the final code to `compensation_failed` and the state to `failed`. A downstream timeout returns HTTP 504; business and compensation failures return HTTP 422.

Idempotency records are written to `/data/idempotency-store.json` before downstream work begins. A completed matching request replays the saved status and response without invoking services again. Reusing a key with another body returns HTTP 409 and `idempotency_payload_mismatch`; a duplicate arriving while the original is active receives HTTP 409 and `idempotency_conflict`. Saga traces are stored separately in `/data/saga-store.json`. Both paths are bind-mounted from the host so container recreation does not erase the records.

## Alternatives considered

A choreographed design would let each service react to events, but the checkout rules require one visible owner for the sequence and the compensation policy. With a coordinator, the ordering, current outcome and reverse actions can be inspected in one place. The cost is that this process becomes an operational dependency.

Running the four requests concurrently would shorten the happy path, but it would break the required business order and make compensation harder to reason about. The sequential approach makes the trace deterministic and prevents shipping or notification from starting after an earlier failure.

Treating compensation as rollback was rejected. A refund is a new payment operation, not erasure of the original charge. Stock release is likewise a new inventory operation. The available mock API does not offer a way to unsend a notification or cancel an already-created shipment, so those are deliberately not represented as compensatable steps.

## Consequences

The caller receives one final result and a chronological trace, and a completed idempotent request can be safely retried after a container restart. The approach is easy to inspect and matches the order's business dependencies, but it keeps the HTTP request open while the downstream services respond and makes the coordinator a component that must be monitored.

The JSON files are persistent across restarts but do not provide multi-process transactions or atomic uniqueness across replicas. If the process is terminated mid-operation, an `in_progress` record can remain and block a replay; this implementation does not claim automatic recovery from an unknown remote outcome. A production system would add recovery for abandoned workflows, transactional storage, concurrency control, and operational alerts for compensation failures.
